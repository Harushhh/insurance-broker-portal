# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Django portal for an insurance broker: it ingests MIS (Management Information System) files from insurers, maps each policy row against a rate-card database to calculate payout, tracks rate-card health/overlap, and exposes dashboards for RTO, Make/Model, Pincode, and Health rate masters, and a Life payout checker fed by the monthly Life workbook (see "Life payout rates" below). An older, separate Next.js app (`life-payout-grid/`, life-insurance commission grids) is still in the repo but is no longer deployed or linked from the portal — see "Life Payout Grid" under Commands.

## Architecture

**Single real Django app: `insurance/`.** `config/` is a legacy scaffold app (a few lines, with a duplicate unused `RateMaster` model and the migration that created its table) — not wired into `project/urls.py` beyond being in `INSTALLED_APPS`. Don't add features there; everything routes through `insurance/`. (The equally empty `dashboard/` scaffold app was deleted.)

- `project/settings.py` / `project/urls.py` — Django project config. Reads all secrets from `.env` (see `.env` keys, never commit values). `DEBUG=False` hard-fails startup if `SECRET_KEY`, `ALLOWED_HOSTS`, or `PARTNER_SSO_TICKET_SECRET` are unset — this is intentional, don't "fix" it by adding defaults.
- `insurance/models.py` — all domain models. Key ones: `RateMaster` (motor rate cards), `HealthRateMaster`, `RTOMaster`, `MakeModelMaster`, `PincodeMaster`, `MISFile`/`MISFailedRow` (uploaded MIS files and rows the mapping engine couldn't resolve), `LockedPolicy`, `SpecialRateRequest`, `RateOverlapScan`/`RateOverlapPair`, `AuditLog`, `MissingMakeModelManualResolution`.
- `insurance/views/` — the request-handling surface, one module per feature (rate_master, rate_master_health, health_rate_master, masters [RTO/Make-Model/Pincode], make_model_mapping, missing_make_model, motor_payout_rates, health_payout_rates, policy_lock, upload, mis_payout, ocr_pipeline, ai_rulebook, grid_management, tickets, special_rates, audit_logs, analysis, user_management, sso_handoff, rate_checker, life_rates, home). `views/__init__.py` re-exports every name the old single `views.py` defined, so `urls.py` still says `views.<name>` and `from insurance.views import RateForm` still works. It was one 8,300-line file before; the banner comments of that file are the module boundaries.
- `insurance/services/` — business logic the views and the API share (make/model matching in `make_model.py`, the Rate Master validity rules in `rate_master_checks.py`, overlap helpers, payout searches, points-audit logging, policy-document OCR processing, ...). Services may take a `request` but never import `views/` or `api/` (`test_structure_guards.LayeringTests`). A few big view functions (`dashboard`, `api_upload_chunk`) still carry inline logic; only request-free helpers were extracted.
- `insurance/access.py` (who may open what: `PAGE_GROUPS`, `RATE_CHECKER_TABS`, the three decorators), `insurance/constants.py` (values two modules must agree on: audit action lists, the health policy-term table, `GRID_INSURER_CHOICES`), `insurance/forms.py` (every form), `insurance/api/` (DRF views, serializers, `urls.py` with `/api/v1/` plus the legacy unversioned aliases, `schema.py`). `docs/` has the longer write-ups (architecture, access-control route table, API, operations, conventions).
- Page CSS/JS that needs no server data lives in `insurance/static/insurance/{css,js}/pages/<template>.ext` (moved verbatim out of the templates, loaded from the same position); blocks that interpolate `{% url %}`/JSON/loops stay inline. `partials/ticket_modal.html` is the one shared HTML fragment. Test runs use plain static storage so they don't need `collectstatic`; production needs it at build time.
- The RTO/Make-Model/Pincode master-data dashboards (`rto_dashboard`/`make_model_dashboard`/`pincode_dashboard` in `views/masters.py`) share one pattern: the page view renders the filter form and an empty table shell only; a sibling `<name>_dashboard_search` JSON endpoint (`?limit=N` for the default "N most recently added/updated" view, unbounded once the user clicks Apply) fills the table via JS; and a `create_<name>` JSON endpoint backs an in-page "Create New Group" modal. This replaced full server-side rendering of the whole table (600-1000+ rows) on every load. `created_at`/`updated_at` on `RTOMaster`/`MakeModelMaster`/`PincodeMaster` (mirroring `RateMaster`'s existing fields) back that ordering — any write path that does `save(update_fields=[...])` on these three models must list `"updated_at"` explicitly, since Django only touches fields named in `update_fields`. The main Rate Master dashboard (`views/rate_master.py::dashboard`) predates this pattern and stays fully server-rendered with GET-param filters and a Django `Paginator`; it separately supports a `page_size` GET param (50/100/200/500, validated against `DASHBOARD_PAGE_SIZE_OPTIONS`, default 50) for rows-per-page; the bulk-update form posts one `selected_groups` field per ticked row, so the largest size has to stay under Django's `DATA_UPLOAD_MAX_NUMBER_FIELDS` (1000, not overridden in `settings.py`), and `test_dashboard_page_size.py` fails if a bigger option breaks "select all" + Bulk Update.
- **Life payout rates** (`views/life_rates.py`, `services/life_workbook.py`, `services/life_rates.py`, `services/life_filters.py`; models `LifeGridUpload` / `LifeRate` / `LifeInsurerNote`). The monthly Life working workbook (`Life_Grid_working-<Mon'YY>.xlsx`, one sheet per insurer plus `Ratemas`/`Sheet3`, 19 insurers) is uploaded on `/life-rate-master/uploads/` (group `Can_View_Life_Rate_Master`) and read **at fixed positions, with no converter**: `services/life_workbook.py` has one `SheetSpec` per insurer sheet (table header text + column letters, found by header text so inserted rows only move a table down), reads the workbook's own calculated **"Final BG" payouts** (`data_only`, so a file saved without values is refused) **and the "Final MG" beside them on the same row** (what the insurer pays the broker; stored as `mg_yr1 … mg_yr6_plus`, migration 0055, found per sheet by a fixed column offset: `SheetSpec.mg_offset` / `Table.mg_offset`, or a hand-listed `Table.mg` map for TATA and Pramerica; a new workbook layout means editing those numbers, and `test_life_mg.py` plus the BG/MG ratio check described there guard them) and the label columns (category / product / variant / PPT / PT / band), never the share or margin columns, and the file itself is not stored. **MG is for the admin pages only**: the Life Rate Master shows it small and grey above the BG in every year cell (and edits, bulk-edits and exports it); the Rate Checker never loads or shows it (`search_life_rates` defers the MG columns, and a test checks the page for it even for an admin). MG and BG are independent stored values: editing one never recomputes the other (no share is stored). An upload made before MG was kept has none; the master says so and the fix is to upload the workbook again. A sheet whose table header is not where its spec expects it stops the whole upload with a message naming the sheet and the header it expected (every broken sheet is named at once; nothing is saved and the live grid is untouched). **Only that one header per table is checked**, the other columns are read by letter: a column inserted inside a table is read wrongly without any warning (found by a probe on 2026-11-14: a test sheet's BG came out 5 for every row instead of 20 / 28 / 55), a renamed or missing sheet goes live without that insurer (a note only, collapsed as "N to look at" on the Uploads page), and a new insurer sheet is not read. That is why the standard file (next bullet) is the way in that does not depend on any layout. Payouts are stored as percent numbers (`35.5` = 35.5 %) in `payout_yr1` / `payout_deferred` ("at 2nd year", the persistency-linked part) / `payout_yr2` .. `payout_yr6_plus`; a written rule in a payout cell ("Only 7 Pay -1.5%") becomes a row `remarks`, spans like "Year 2 & 3" fill each year they cover, `unit` is 1.0 only for LIC (whole percents). Each upload is a `LifeGridUpload`; the newest is active (`is_active`, one at a time) and earlier ones stay so an admin can **Make live** again. `/life-payout-rates/` (the Life tab of the Rate Checker, group `Can_View_Life_Payout_Grid`, last in `RATE_CHECKER_TABS`) searches the active upload with **fixed filter lists**: Category (PAR, NON PAR, TERM, ULIP, TULIP, ANNUITY / SAVINGS, PENSION), Payment Mode (SP, LP, RP), PPT (1-13, >13), PT (1-100, searchable), plus Insurer, Product (narrowed from the insurer and category) and free text (every word must match); results are ranked by first-year payout (blanks last), capped at `LIFE_MAX_RESULTS`, with the insurer's notes under the table. The results table (`partials/life_rate_table.html`, styled by `life_table.css`, shared with the Rate Master) never scrolls sideways (the Health stylesheet it borrows would make it ~2000px wide): the text columns wrap and the numbers stay on one line, and when the card is under 940px wide (a container query on `.life-results-host`; the sidebar and paddings leave only ~940px on a 1440px screen, and a row full of long values such as `0.4237%` needs ~905px) each row becomes a small card instead, so adding a column means re-checking that breakpoint. The workbook writes categories, PPT and PT as free text, so `services/life_filters.py` is the **mapping layer** from the fixed values to a row's own wording; it runs in Python over the rows the SQL filters (insurer, product, words) leave, nothing extra is stored, and edits and old uploads follow the rules at once. Its docstring is the spec (the user's rules, 2026-11-13): a row can sit in several categories (a plan named "...Pension..." is also PENSION, a row worded "Annuity" stays in ANNUITY / SAVINGS too; rows with no wording are sorted by Term / Annuity / TULIP / ULIP / Pension in the plan name; ILP rows and rows that say nothing show only with no Category); a PPT pick is numeric coverage of the wording ("7 to 9", "10+", "12 & Above"), and `>13` means a row that reaches 14 or more; Payment Mode SP = the single-pay wording plus a PPT of exactly 1 (the PPT field is hidden and ignored), RP = the regular-pay wording, LP = every PPT number or range of 2+ years plus the "Limited" wording (the PPT pick narrows LP); with a PPT picked and no mode, rows worded SP / RP / Limited are left out and rows that state no PPT (blank, "All") stay; a PT pick is numeric coverage, and a blank, "Any", "RP" or whole-life PT matches any. A value the page does not offer counts as not picked. Digit's Glow Plus rows carry their mode in the variant column, not the PPT, so a Payment Mode pick does not find them. **The checker edits nothing**: no Edit column, link or "edited" tag, for anyone (`test_the_checker_never_edits_anything_whoever_looks_at_it`). Everything is viewed and edited on the **Life Rate Master** (`/life-rate-master/`, group `Can_View_Life_Rate_Master`, the Life tab of Rate Master) with three sections: *Payout rows* (every stored row of the live upload, or of another via `?upload=<id>`, in workbook order with all seven year columns, each showing the MG small and grey above the BG; filters on insurer, the category as stored, words (also the workbook cell such as `TATA!A17`) and edited-only; 50/100/200 per page; an Edit button per row to `/life-rate-master/edit/<id>/`, which returns to the same filtered page through `?next=`), *Insurer notes* (`/life-rate-master/notes/`: the `LifeInsurerNote` text per insurer, Edit, and Add notes for an insurer whose sheet had none; an emptied note disappears from the checker) and *Uploads* (`/life-rate-master/uploads/`: the standard-file and old-workbook upload forms, the history with Review / Discard for an upload that is waiting, View rows, Make live, and Delete for an earlier upload). Insurer, sheet, section and workbook cell are shown but not editable. Besides the single-row Edit, *Payout rows* has four more tools. **Add row** (`/life-rate-master/add/`): the row goes after the last row of its insurer (a new insurer goes last), takes `source_ref` = `LifeRate.MANUAL_SOURCE_REF` ("Added on screen"), is stamped edited, and the page tags it "added"; it needs an insurer, a product and one payout. **Delete** (POST, a button on the edit page behind a confirm): the audit entry keeps every value, so the row can be typed in again. **Bulk edit** (tick boxes, or "select all N matching rows", which the server works out again from the page's filters and refuses if the count changed since the page loaded): the whitelist is `BULK_FIELD_LABELS` in `services/life_rates.py` (the seven MG and the seven BG payouts plus category / product / variant / PPT / PT / condition / remarks; identity (id, upload, insurer, sheet, section, workbook cell, position) and the edit stamps are refused); payouts take set / add points / multiply / clear, text takes set / clear (remarks also append); `plan_bulk_update` works out every row before anything is saved, rounds a payout to 4 decimals (Decimal arithmetic), skips blank payouts on add / multiply, and refuses the whole operation if any row would leave 0-100 or exceed a field's length, so a bulk edit never half-applies. **Export Excel** (`/life-rate-master/export/`): every row matching the page's filters (not only the page shown), header = the stored field names (the Motor / Health convention), payouts as plain percent numbers. Add, Delete and Bulk edit are audited as `LIFE RATE ADD` / `LIFE RATE DELETE` / `LIFE BULK UPDATE` (in `SECURITY_AUDIT_LOG_ACTIONS`, so they show on the Security Audit page and follow its 7-day retention); Add and Delete keep `LifeGridUpload.row_count` / `insurer_count` in step. MG and BG are both stored but no share, hash or pinned BG is, so bulk edit changes MG values or BG values directly (never recomputing the other) and the export has no `calc_*` columns: every stored MG and BG value is a plain column (`mg_yr1 … mg_yr6_plus`, then `payout_yr1 … payout_yr6_plus`). A change lives on that upload's own row (`is_edited`, audited as `LIFE RATE EDIT` / `LIFE NOTE EDIT` too), so **the next upload starts clean**, rows added on screen included. Not built: search logging (`LIFE_POINTS_SEARCH`), a REST endpoint, and recomputing the BG from the MG and a share (the workbook's own results are authoritative; its `Ratemas` rounding table has 21 hand-typed rows that make 287 payout cells differ from a plain half-up rule, and they come through as the workbook shows them). Tests: `insurance/test_life_rates.py` and `insurance/test_life_mg.py` (the reader is tested on small workbooks laid out like the real Edelweiss / LIC / Bajaj / TATA / PNB / IndiaFirst sheets, because the real workbook holds insurer rates and is not in the repo; the MG column offsets were checked against the real file by comparing every row's BG with the MG it comes from: BG is about 75 % of MG in the first year and about 50 % in the renewals on every sheet, and the few rows that differ are the workbook's own hand-typed BG cells, such as Axa's Guaranteed Bachat at 0). When the workbook layout changes, edit the matching `SheetSpec`.
- **Life standard file and the review of an upload** (`services/life_standard.py`, `services/life_review.py`, the views in `views/life_rates.py`, `life_rate_master_review.html`, `LifeGridUpload.is_pending` from migration 0058; added 2026-11-14 because "anything can change" in an insurer's grid and a fixed per-sheet reader cannot follow it). The way in that does not depend on any insurer's layout: one flat table whose header row names its columns (the stored field names, the Motor / Health CSV convention) and which are found **by name**, so nothing can shift. Columns: `insurer`, `category`, `product`, `variant`, `ppt`, `pt`, `condition`; the validity dates `from_date`, `to_date` (below); the BG payouts `payout_yr1`, `payout_deferred`, `payout_yr2` .. `payout_yr5`, `payout_yr6_plus` (at least one, unless the row is a written rule that is not a number, which goes in `remarks`: the live Oct'26 grid has 3 such rows, Axis Max and LIC, so an export of it has to load back); the MG `mg_yr1` .. `mg_yr6_plus` (optional); `remarks`; the optional trace columns `sheet`, `section`, `source_ref` (a blank one, or one that only says `Row N` / `Added on screen`, becomes `Row N` of this file). Order, case and punctuation of a header do not matter; the columns an Export Excel adds (`id`, `upload`, `position`, `is_edited`, `edited_by`, `edited_at`) are ignored, so **an Export Excel is itself a valid standard file** (it carries a `Notes` sheet too): export, edit, upload back. Payouts are percent numbers (35.5 = 35.5 %; a cell Excel shows as 35.5 % is read as 35.5, the text "35.5%" too; blank = none, 0 = zero); an optional `Notes` sheet (`insurer`, `note`) carries the insurer notes; `.xlsx` or `.csv` (UTF-8 / Windows-1252, comma / semicolon / tab). `read_standard_file` checks the whole file and raises `LifeFileError` listing every problem with its row number (batch collection, like the MIS engine): empty insurer / product, no BG payout and no rule in `remarks`, a payout that is not a number or is outside 0-100, text over the stored length, an Excel error, a date where a PPT / PT should be (Excel turns `5-10` into one; the template formats those columns as Text), an insurer spelled two ways, a repeated column, bad Notes rows; unknown columns, extra sheets, exact copies and notes for a stranger are only warnings. It returns the same `LifeWorkbook` as the workbook reader, so `save_life_upload` stores both the same way. A standard upload is stored **not live** (`save_life_upload(make_live=False)` sets `is_pending`; the live grid is untouched; the Rate Checker and the MIS engine read `is_active` only, so they never see it) and opens `/life-rate-master/uploads/<id>/review/`, which `review_upload` builds by reading both uploads (it writes nothing): the rows added / removed / changed against the live grid (a row's identity is insurer, section, category, product, variant, PPT, PT and condition with case and spacing ignored; identical rows are matched first, so a reordered grid shows nothing, and several rows with one identity pair in order), a table by insurer (an insurer the upload no longer has, one that lost a quarter of its rows, a new one, one spelled differently from the live grid), and checks (a BG above its own MG, a BG that moved by 10 points or more, PPT / PT wording that `life_filters.ppt_unreadable` / `pt_unreadable` cannot read, plan mappings and insurer aliases that would stop reaching the grid, rows with no first-year payout, rows that are only a written rule). Make live is the existing `activate_life_upload` (it clears `is_pending`); Discard (`discard_life_upload`) deletes only a pending upload, never the live grid or history. **Delete** (`delete_life_upload`, route `life_rate_master_delete_upload`, the red button on an earlier upload's row of the Uploads tab; added 2026-11-14 so the user can clean up test uploads) removes any upload that is not live, an earlier one or a pending one, with its rows and notes: the live grid is refused ("make another upload live first": the Rate Checker and the MIS engine read it, and a delete never promotes another upload by itself), the row is re-read under a lock so a page that is out of date cannot delete what another tab has just made live, the live row shows a greyed-out Delete and a pending row keeps Discard, and it is audited as `LIFE GRID UPLOAD` ("Deleted an earlier upload '...'"), same gate as Make live. Tests: `insurance/test_life_upload_delete.py`. The old workbook upload stays: live at once, unless its "show me what changed first" box is ticked, which stores it pending too. `ppt_unreadable` / `pt_unreadable` exist because a wording with words but no number ("Five Pay") reads as "states nothing" and so applies to every PPT / PT. **Validity dates** (added 2026-11-14, migration 0059, mirroring Motor and Health): `LifeRate.from_date` / `to_date`, the standard-file columns of the same names (`valid_from` / `valid_to` / `valid_till` are accepted spellings), both ends included, blank = no limit on that side, so a row with neither applies to any date and **a grid with no dates behaves exactly as before** (the real Sept'26 check came out identical: 159 matched, 364 no plan name ...). A cell is an Excel date, `DD/MM/YYYY` or `YYYY-MM-DD` (`health_grid_utils.parse_grid_date` plus a few pandas / Windows spellings; a two-digit year is refused, not guessed), `from_date` after `to_date` is refused. Where they are used: the Rate Checker's **Date** box (`target_date`, like Health Payout Rates: rows that apply on it, empty = every row, an unreadable value is ignored), the **MIS engine** (`life_mis._narrow_by_date`, stage `date`, label `Policy: inception date` like Health's RULE H2: after the plan and before PPT; the policy's `Policy: inception date` read day first; a blank or unreadable inception leaves only rows with no dates; a matched reason names the row's dates), the Edit / Add forms (`from_date`, `to_date`, an end before the start is refused), the export (real date cells, `DD/MM/YYYY`), the tables (a "Valid ..." line under the plan name) and the review (dates are not part of a row's identity, so a changed window is a "changed" row; a warn check for date windows of one plan that overlap with different payouts, info checks for rows already past their end date and rows not started yet). Not built: bulk edit of the dates (use the standard file), reading a date out of the old workbook (a note like "Valid till 30th Nov" stays a remark: never guessed), a converter per insurer (those live outside the portal, like the Motor / Health grid tools). Tests: `insurance/test_life_standard_file.py`.
- **Life one-sheet export for a dashboard** (`services/life_dashboard.py`, the **Dashboard** tab `/life-rate-master/dashboard/` and its download `/life-rate-master/dashboard/download/` in `views/life_rates.py`, `life_rate_master_dashboard.html`; added 2026-11-14 when the user wanted ALL the data in ONE sheet with no blank cell and no placeholder, and next month's grid to be easy). Nothing is stored: `dashboard_data(upload, include_mg=True)` reads the upload's `LifeRate` rows every time, so a new month is just upload, Make live, download. One row = one plan in one year as BG or MG; columns `grid, plan_id, insurer, product, plan, ppt, payout_type, payout_year, year_order, payout_pct` (a FIXED schema: a column that comes and goes breaks a dashboard refresh). Gap rules: a year with no payout has no row; variant / condition / section / `PT n` are merged into `plan` (so insurer + plan + ppt is unique; a collision gets ` | row <id>`); columns only some plans have (category, remarks, PT as a column) are NOT in the sheet (category is stated for 65% of the Oct'26 plans, PT 30%, remarks 34%, and the workbook states no category for IndiaFirst, LIC, PNB, Shriram or SUD: nothing can fill it without a made-up value; the standard file and Export Excel keep them); a plan that cannot be a row is left out and listed on the tab (no payout number = a written rule; no PPT stated = `-` or empty cell, no product name); two restatements are listed as restated (a blank PPT whose Variant reads as a pay term by `life_filters.ppt_spec`, Digit Glow Plus; a blank PPT whose product name has `N - M`, Tata `ILP 7 - 9`). These two live in the export, not in `services/life_workbook.py`: fixing the reader instead (merged Variant/PPT cell, Tata `ILP` names without "Pay") would put the right PPT in the Master and the Rate Checker too, and is the cleaner permanent fix. `?mg=0` (button "Download BG only") drops the MG rows: **MG is admin only**, use it for any dashboard partners or non-admins can open. On the real Oct'26 grid it gives 1,512 plans, 9,930 rows (BG 4,985, MG 4,945), 8 left out, 5 restated, identical cell by cell to the nine-sheet workbook built first and to the export it came from. Tests: `insurance/test_life_dashboard.py`.
- **Life rows in the MIS Payout Engine** (`services/life_mis.py` holds the rules, `mapping_engine._match_life_row` turns the answer into the row's output, `views/life_mis_mapping.py` with `life_mis_plans.html` / `life_mis_insurers.html` are the **Life Mapping** screens at `/life-mis-mapping/`, group `Can_View_MIS_Payout_Engine`; models `LifeInsurerAlias` / `LifePlanMapping`, migration 0056, and 0057 seeds the 16 insurer spellings of the real MIS). A MIS row with `Product` = `life` is matched to the **live Life upload** (`LifeRate`) and its **first-year BG payout is printed in `Porate`** (`Potype` `On Premium - Year 1`; `Displaygroupid` = the `LifeRate` id; the grid row, the upload label and how the plan was found are in the Failure Reason). The deferred second-year part and any condition or remark of the grid row are only text in `Addtnc` (`Manual Review Required: ...` for conditions and remarks), never added in or applied. A NO MATCH `Failure Reason` is `Failed on: <label> — <detail> | Also failed on: <label> — <detail> | …` on ONE line (`format_failed_on` / `split_failed_on`): the first segment is byte-for-byte what a row stopping at its first failure always had, because the Missing Make/Model page filters on the start of the text (`MAKE_MODEL_UNRESOLVED_REASON_PREFIX`) and the coverage-gap panel parses it — a new rule's failure text must keep that shape and contain no newline. RULE 3's vehicle age is calculated, not read from `Policy: vehage` (and no longer from `Policy: manufacturing year`): `calculate_vehicle_age` = (the current calendar year (`timezone.localdate().year` when the run happens — 2026 now, 2027 next year) + 1) − a year, in whole years. The year is the 4-digit year in `Policy: date of registration` (dd-mm-yyyy; only the year is read, so day/month order never matters) for a standard/rollover policy, and the year in `Policy: inception date` for a new vehicle — `Policy: sub product` in `NEW_VEHICLE_SUB_PRODUCTS` (`1+3`, `1+5`). An age outside every band quotes the age first in its failure detail (`Calculated vehicle age '2' …`) because the coverage-gaps panel groups on the first quoted value. The age is matched against each rate row's band as `(vehicle_age_min, vehicle_age_max]` — lower bound EXCLUSIVE, upper bound inclusive — so the current year's registrations (age 1) always fall in the `0-1` slab, age 2 in `1-2`, and an age on a whole-number seam (`0-1` | `1-5.01`) belongs to the lower band only; `x.01` bounds behave as they read (`0-1.01` covers age 1, `1.01-5.01` starts at age 2). ### Soft delete and status conventions
- `RateMaster.is_deleted` is a `CharField` `"YES"/"NO"` (not a boolean) and `RateMaster.status` is `"ACTIVE"/"INACTIVE"` — both `db_index=True`. Filter on the string values, not truthiness.
- The Rate Master / Health Rate Master grid pages themselves still display soft-deleted rows; it's the *downstream* pages (dashboards, payout lookups, mapping engine) that must exclude `is_deleted="YES"`. When adding a new read path over these tables, check which behavior it should match.

### Access control
The Access Control "Rate Checker" checkbox stands for Motor + Health only (`RATE_CHECKER_GROUPS` in `access.py`, mirrored in `user_management.js`); Life has its own checkbox ("Life Payout Rates", plus "Life Rate Master"), because folding it into the bundle would make every Motor + Health user show unticked and lose both on the next save. The two Life groups are created by migration `0053_seed_life_groups`, which grants them to nobody.

Permissions are real Django `Group` objects, managed at `/user-management/` (`staff_required`-gated) and enforced via `page_access_required` (defined in `insurance/access.py`, applied in `insurance/urls.py`). Group names are stable identifiers referenced by migrations (e.g. `insurance/migrations/0021_seed_page_access_groups.py`) — don't rename a permission group to "clean it up"; it silently revokes access for everyone already assigned. `insurance/context_processors.py::sidebar_access` re-derives the same rules to decide sidebar visibility — a change to who can access a page belongs in both places.

### Business-rule ambiguity
Several features here encode a general rule plus named special cases (e.g. Rate Master Pi/Po margin exemptions, tariff/cc/sc rounding scope). When a new request could combine a general rule and a special case, they combine additively (AND), not as an override — confirm this reading explicitly when a change touches one of these rule sets, and ask up front if a request is ambiguous across more than one axis (e.g. which fields *and* which condition).

`.env` (gitignored) supplies: `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`, `DB_HOST`/`DB_NAME`/`DB_USER`/`DB_PASSWORD`/`DB_PORT` (falls back to SQLite if `DB_NAME` unset, or `DATABASE_URL` wins if set), `EMAIL_HOST`/`EMAIL_PORT`/`EMAIL_HOST_USER`/`EMAIL_HOST_PASSWORD`/`EMAIL_USE_TLS`, `GEMINI_API_KEY` (AI OCR extraction), `PARTNER_SSO_TICKET_SECRET` (the old `LIFE_PAYOUT_GRID_*` keys are no longer read), `CSRF_TRUSTED_ORIGINS` (optional; defaults to the production hostname). Media storage auto-switches to Cloudflare R2 (S3-compatible) when `AWS_STORAGE_BUCKET_NAME`/`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` are all set, otherwise falls back to local disk. Optional `GRID_ARCHIVE_BUCKET_NAME` puts the Grid Management archive in a separate bucket (same credentials must reach it). Deployed on Railway (see `Procfile`). `.env.example` lists every variable.
