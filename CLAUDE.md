# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Django portal for an insurance broker: it ingests MIS (Management Information System) files from insurers, maps each policy row against a rate-card database to calculate payout, tracks rate-card health/overlap, and exposes dashboards for RTO, Make/Model, Pincode, and Health rate masters. A separate Next.js app (`life-payout-grid/`, life-insurance commission grids) is still in the repo but is no longer deployed or linked from the portal — see "Life Payout Grid" under Commands.

## Commands

Run from the repo root with the venv active (`venv\Scripts\python.exe` on Windows, no separate activation needed if invoking that binary directly).

```bash
python manage.py runserver 127.0.0.1:8000    # dev server (also runnable via .claude/launch.json "django-dev")
python manage.py test                         # full test suite (plain Django TestCase, no pytest)
python manage.py test insurance.tests.UrlAuthGateTests   # single test class
python manage.py test insurance.tests.UrlAuthGateTests.test_something  # single test method
python manage.py test insurance.test_overlap_utils        # overlap-detector tests (separate file, not in tests.py)
python manage.py test insurance.test_structure_guards     # layout / API-alias / staff-only-docs / import guards
python manage.py show_access_matrix                       # Markdown table of who may open each route
python manage.py makemigrations insurance
python manage.py migrate
python manage.py createcachetable             # required once — DB-backed cache for login throttling
```

Life Payout Grid (separate Next.js app, its own `node_modules`). **Decommissioned 2026-10-11:** its Railway service was deleted and the portal's side of the integration is commented out (`urls.py` routes, `views/rate_checker.py` handoff views, the `LIFE_PAYOUT_GRID_*` block in `settings.py`, the Life tab in `rate_checker_tabs.html`, the "Update Payout Rates" sidebar link, and Life in `RATE_CHECKER_TABS` / the partner SSO allow-list). ## Architecture

**Single real Django app: `insurance/`.** `config/` is a legacy scaffold app (a few lines, with a duplicate unused `RateMaster` model and the migration that created its table) — not wired into `project/urls.py` beyond being in `INSTALLED_APPS`. Don't add features there; everything routes through `insurance/`. (The equally empty `dashboard/` scaffold app was deleted.)

- `project/settings.py` / `project/urls.py` — Django project config. Reads all secrets from `.env` (see `.env` keys, never commit values). `DEBUG=False` hard-fails startup if `SECRET_KEY`, `ALLOWED_HOSTS`, or `PARTNER_SSO_TICKET_SECRET` are unset — this is intentional, don't "fix" it by adding defaults.
- `insurance/models.py` — all domain models. Key ones: `RateMaster` (motor rate cards), `HealthRateMaster`, `RTOMaster`, `MakeModelMaster`, `PincodeMaster`, `MISFile`/`MISFailedRow` (uploaded MIS files and rows the mapping engine couldn't resolve), `LockedPolicy`, `SpecialRateRequest`, `RateOverlapScan`/`RateOverlapPair`, `AuditLog`, `MissingMakeModelManualResolution`.
- `insurance/views/` — the request-handling surface, one module per feature (rate_master, rate_master_health, health_rate_master, masters [RTO/Make-Model/Pincode], make_model_mapping, missing_make_model, motor_payout_rates, health_payout_rates, policy_lock, upload, mis_payout, ocr_pipeline, ai_rulebook, grid_management, tickets, special_rates, audit_logs, analysis, user_management, sso_handoff, rate_checker, home). `views/__init__.py` re-exports every name the old single `views.py` defined, so `urls.py` still says `views.<name>` and `from insurance.views import RateForm` still works. It was one 8,300-line file before; the banner comments of that file are the module boundaries.
- `insurance/services/` — business logic the views and the API share (make/model matching in `make_model.py`, the Rate Master validity rules in `rate_master_checks.py`, overlap helpers, payout searches, points-audit logging, policy-document OCR processing, ...). Services may take a `request` but never import `views/` or `api/` (`test_structure_guards.LayeringTests`). A few big view functions (`dashboard`, `api_upload_chunk`) still carry inline logic; only request-free helpers were extracted.
- `insurance/access.py` (who may open what: `PAGE_GROUPS`, `RATE_CHECKER_TABS`, the three decorators), `insurance/constants.py` (values two modules must agree on: audit action lists, the health policy-term table, `GRID_INSURER_CHOICES`), `insurance/forms.py` (every form), `insurance/api/` (DRF views, serializers, `urls.py` with `/api/v1/` plus the legacy unversioned aliases, `schema.py`). `docs/` has the longer write-ups (architecture, access-control route table, API, operations, conventions).
- Page CSS/JS that needs no server data lives in `insurance/static/insurance/{css,js}/pages/<template>.ext` (moved verbatim out of the templates, loaded from the same position); blocks that interpolate `{% url %}`/JSON/loops stay inline. `partials/ticket_modal.html` is the one shared HTML fragment. Test runs use plain static storage so they don't need `collectstatic`; production needs it at build time.
- The RTO/Make-Model/Pincode master-data dashboards (`rto_dashboard`/`make_model_dashboard`/`pincode_dashboard` in `views/masters.py`) share one pattern: the page view renders the filter form and an empty table shell only; a sibling `<name>_dashboard_search` JSON endpoint (`?limit=N` for the default "N most recently added/updated" view, unbounded once the user clicks Apply) fills the table via JS; and a `create_<name>` JSON endpoint backs an in-page "Create New Group" modal. This replaced full server-side rendering of the whole table (600-1000+ rows) on every load. `created_at`/`updated_at` on `RTOMaster`/`MakeModelMaster`/`PincodeMaster` (mirroring `RateMaster`'s existing fields) back that ordering — any write path that does `save(update_fields=[...])` on these three models must list `"updated_at"` explicitly, since Django only touches fields named in `update_fields`. The main Rate Master dashboard (`views/rate_master.py::dashboard`) predates this pattern and stays fully server-rendered with GET-param filters and a Django `Paginator`; it separately supports a `page_size` GET param (50/100/200, validated against `DASHBOARD_PAGE_SIZE_OPTIONS`, default 50) for rows-per-page.
- Make/Model Mapping (`/make-model-mapping/`, `MakeModelMapping`/`MakeModelMappingValue`, gated by `Can_View_Make_Model_Dashboard`) links spellings of one vehicle that different insurers' `MakeModelMaster` clusters write differently ("HERO SPLENDOR" vs "HERO MOTOCORP SPLENDOR"); each spelling can belong to only one mapping (`value` is unique), and clusters are never rewritten. The make/model search paths — Rate Master dashboard filter + export, Motor Payout Rates, Policy Lock Checker (page and API) — resolve a picked value through `services/make_model.py::resolve_make_model_groups`, which expands it to every linked spelling; any new make/model search path should call that rather than hand-rolling a `strict_match_in_cluster` loop. The MIS mapping engine and overlap detector deliberately don't use it (they have their own word-overlap matching and must stay in sync with each other).
- `api_upload_chunk`'s `rate_master` branch (`views/upload.py`) processes up to 2500 rows per chunk from a client-side chunked upload (`upload.html`) — any per-row `.filter()`/`.exists()`/`.get()` added there must become a single query before the loop, cached into a dict/set, or a large file will blow past the request timeout (this has happened in production). `upload_batch_id` — fresh on every click of "Start Upload" — is deliberately part of `GROUP_FIELDS`/`build_key_hash`, so retrying an upload always creates new `RateGroup`s rather than recognizing rows an earlier, partially-successful attempt already saved; `CsvUploadAttempt` plus `api_check_duplicate_upload`/`api_complete_upload` (the browser SHA-256-hashes the raw file before parsing it) warn — but don't block — when the same file was already attempted for that target table.
- `grid_management`'s `GridDocument` uploads dispatch the actual file write to storage (Cloudflare R2 in production) to the Celery task `save_grid_document_file_task` rather than saving inline — a slow/hung storage write previously pinned a gunicorn worker for the whole request timeout, and `Procfile`'s worker/thread count is deliberately modest, so that alone could starve every other page on the site. New file-upload code should follow the same pattern. Grid uploads are kept active for `GRID_RETENTION_MONTHS` (3: current month + 2 previous, so on 1 Oct, July and older go) and then moved by `insurance/grid_archive.py` into `STORAGES["grid_archive"]` (a `grid_archive/` prefix in R2, or its own bucket via `GRID_ARCHIVE_BUCKET_NAME`) — file copied and read back (SHA-256), an immutable `manifest-<ts>.json` written per run (one per run, never overwritten, so a partial run can't clobber an earlier one), and only then are the rows and original files deleted; anything that fails verification stays put and is retried next run. The manifests alone are enough to rebuild the rows (`GridArchiveBatch` is just a log), and the job refuses to purge unless R2 is configured. `restore_grid_documents` has two modes: `--source archive` (full fidelity) and the default `--source live`, which re-creates rows for files still under `grid_documents/` that no row points at — only the file survives that, so insurer is guessed from the filename, and remarks/status/uploader/work-effected date are lost. Note the Grid Management page filters to the *current month* by default, so on the 1st of a month it looks empty until "All Months" is chosen — check that before assuming data was lost.
- `insurance/urls.py` — every route wrapped in one of three access decorators defined in `insurance/access.py` (urls.py imports them; the REST routes come from `insurance/api/urls.py`, spliced in before the catch-all): `staff_required` (is_staff/is_superuser/ADMIN group), `super_admin_required` (SUPER_ADMIN group only — its only user was the Life Payout Grid admin handoff, now disabled, so no route uses it today), `page_access_required(group_name)` (ADMIN group OR the named per-page group, checked against real Django `Group` membership set via `/user-management/`). A handful of server-to-server API routes deliberately skip these and use `HasAPIKey` instead. `insurance/tests.py::UrlAuthGateTests` enforces that every new route stays gated — update `PUBLIC_URL_NAMES` there only for genuinely public pages.
- `insurance/mapping_engine.py` — the MIS-to-RateMaster matching engine (`process_mis_mapping`), a RULE 1-6 sequential-filter chain (insurance company, product, vehicle age, make/model fuzzy match via `rapidfuzz`, RTO, etc.) that narrows a rate-card queryset down to the matching row(s) for a policy. When a rule empties the queryset, that rule's label+detail becomes the stored `MISFailedRow.failure_reason`. The MIS `Product` column is checked first for every row and alone picks the table: `motor` → `RateMaster` (the BAD DATA guard + RULE 1-6 chain), `health` → `HealthRateMaster` (`_match_health_row`), anything else (blank, `non_motor`, `life`, a typo) → `❌ NO MATCH` with a `Failed on: Product —` reason and no rate lookup. Routing tests: `insurance/test_mapping_engine_routing.py`. RULE 2's product, sub product and fuel checks (`check_exact_match`) are exact, case-insensitive matches — no substring/fuzzy (the fuzzy scorer rated `GCV 3W`/`GCV 4W` at 83.3 vs a threshold of 75, so sibling products co-matched); a blank rate-card value is still a wildcard. Health's `product_name`/`policy_category`/`business_type` still use the fuzzy `check_categorical_match`. Tests: `insurance/test_mapping_engine_exact_match.py`. RULE 3's vehicle age is calculated, not read from `Policy: vehage`: `calculate_vehicle_age` = the current calendar year (`timezone.localdate().year` when the run happens — 2026 now, 2027 next year) − `Policy: manufacturing year`, in whole years, and it is matched against each rate row's band as `[vehicle_age_min, vehicle_age_max)` — lower bound inclusive, upper bound exclusive, so `0-1`, `1-2`, `2-3` bands each own exactly one age, while `x.01` bands still cover the whole number below them. CC/GVW, seating capacity and tariff stay inclusive on both ends. Tests: `insurance/test_mapping_engine_age.py`. When RULE 1-6 leaves several distinct rate groups, the row is only `⚠️ MULTIPLE MATCHES` if their rates differ: if every matched row carries the same payout rate *and* payin rate (`payout_signature`: the rate type (`Potype`/`Pitype` — it picks the premium base, so `On OD` 10 ≠ `On Net` 10) and the consolidated Porate/Pirate value per side, plus the raw OD/TP pair for `On OD and TP`, which is split-calculated; nothing else — not T&C or flat amount, since RULE 1-6 already picked these rows), the lowest Group ID is used and the row is a normal `✅ MATCH` with that noted in `Failure Reason` and the run summary. Health (`_match_health_row`) follows the same rule over its own rate shape: rows whose tenure-column payout rate (`rate_col`) and `payin_rate` are both equal collapse to the lowest `HealthRateMaster` id (`health_matched_rows_share_one_rate`; Health has no rate-type column to compare, and the other tenures' columns are ignored). A collapsed Health row carries a private `_tied_rows` key that the caller pops, to count it in the run summary. `overlap_utils` still flags such pairs (they are still redundant cards); it does not know about this. Tests: `insurance/test_mapping_engine_identical_payout.py`.
- `insurance/overlap_utils.py` — the Rate Master Health overlap detector. Its predicates deliberately mirror `mapping_engine`'s RULE 1-6 semantics exactly (blank = wildcard, 0 = a real bound, YES/NO disjoint) so it flags every pair of rate rows the mapping engine could match ambiguously, before an MIS file ever hits them. Changing a rule in one file without the equivalent change in the other will desync detection from reality.
- `insurance/health_grid_utils.py` — identity-hash/parsing helpers shared between the one-off Excel import command and the web bulk-upload endpoint for `HealthRateMaster`, so both agree on what makes two rows duplicates.
- `insurance/sso.py` + `api/views.py::IssueSSOTicketAPIView` / `views/sso_handoff.py::sso_consume_view` — inbound SSO handoff from an external partner portal (ArhamSecure), signed with `PARTNER_SSO_TICKET_SECRET`. The partner may request the `Rate_Checker` bundle (Motor + Health); `Can_View_Life_Payout_Grid` is no longer grantable (requests naming it are clamped away, not rejected). It was once modelled on the *outbound* handoff into the `life-payout-grid` app, which used a separate `LIFE_PAYOUT_GRID_AUTH_SECRET` and is now disabled.
- `insurance/utils.py` — Gemini OCR extraction helpers (`extract_data_with_gemini`). The never-called `auto_reconcile_mis` LockedPolicy cross-check was deleted.
- `insurance/auth_views.py` — login/signup views with cache-backed attempt throttling (5 attempts/15 min for login, 10/hour for signup); a broken cache backend must fail open, not lock users out — this is why `createcachetable` is required setup, not optional.
- `insurance/context_processors.py` — `sidebar_access` mirrors the same ADMIN/per-page-group rules as `page_access_required`/`staff_required` in `access.py` to decide which sidebar links render. A second place encoding access rules — keep it in sync when those decorators change (`SidebarMatchesPageGateTests` fails if they drift).
- `insurance/tasks.py` — Celery tasks: the two scheduled log-cleanup jobs registered in `CELERY_BEAT_SCHEDULE` (also runnable ad hoc via the `cleanup_points_search_logs`/`cleanup_security_audit_logs` management commands), the monthly `archive_old_grid_documents` (03:00 on the 1st; ad hoc via `archive_grid_documents [--dry-run]`), plus async work queued from the views (`process_policy_document_task` calls `services/policy_documents.py`) — `process_mis_mapping_task`, `process_policy_document_task`, `save_grid_document_file_task`, `run_rate_overlap_scan_task`.
- `insurance/management/commands/` — one-off/maintenance scripts: `dedupe_rate_master`, `find_duplicate_rate_master` (read-only duplicate scan, writes nothing; both accept `--cross-group --status ACTIVE|INACTIVE`, default `ACTIVE`, to decide which status counts as a duplicate — a repeated bulk-upload attempt lands as `INACTIVE`, so cleaning that up needs `--status INACTIVE` explicitly), `purge_deleted_rate_master`, `regroup_rate_master`, `run_overlap_scan`, `import_health_rate_master`, `migrate_media_to_object_storage`, `cleanup_points_search_logs`, `cleanup_security_audit_logs`, `archive_grid_documents`, `restore_grid_documents` (both take `--dry-run`).
- Templates live in `insurance/templates/` (mostly flat, a few in `insurance/templates/insurance/`, `partials/`, and `registration/`). `base.html` is the authenticated shell; `base_auth.html` is the login/signup shell.

### Soft delete and status conventions
- `RateMaster.is_deleted` is a `CharField` `"YES"/"NO"` (not a boolean) and `RateMaster.status` is `"ACTIVE"/"INACTIVE"` — both `db_index=True`. Filter on the string values, not truthiness.
- The Rate Master / Health Rate Master grid pages themselves still display soft-deleted rows; it's the *downstream* pages (dashboards, payout lookups, mapping engine) that must exclude `is_deleted="YES"`. When adding a new read path over these tables, check which behavior it should match.

### Access control
Permissions are real Django `Group` objects, managed at `/user-management/` (`staff_required`-gated) and enforced via `page_access_required` (defined in `insurance/access.py`, applied in `insurance/urls.py`). Group names are stable identifiers referenced by migrations (e.g. `insurance/migrations/0021_seed_page_access_groups.py`) — don't rename a permission group to "clean it up"; it silently revokes access for everyone already assigned. `insurance/context_processors.py::sidebar_access` re-derives the same rules to decide sidebar visibility — a change to who can access a page belongs in both places.

### Business-rule ambiguity
Several features here encode a general rule plus named special cases (e.g. Rate Master Pi/Po margin exemptions, tariff/cc/sc rounding scope). When a new request could combine a general rule and a special case, they combine additively (AND), not as an override — confirm this reading explicitly when a change touches one of these rule sets, and ask up front if a request is ambiguous across more than one axis (e.g. which fields *and* which condition).

## Environment

`.env` (gitignored) supplies: `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`, `DB_HOST`/`DB_NAME`/`DB_USER`/`DB_PASSWORD`/`DB_PORT` (falls back to SQLite if `DB_NAME` unset, or `DATABASE_URL` wins if set), `EMAIL_HOST`/`EMAIL_PORT`/`EMAIL_HOST_USER`/`EMAIL_HOST_PASSWORD`/`EMAIL_USE_TLS`, `GEMINI_API_KEY` (AI OCR extraction), `PARTNER_SSO_TICKET_SECRET` (the old `LIFE_PAYOUT_GRID_*` keys are no longer read), `CSRF_TRUSTED_ORIGINS` (optional; defaults to the production hostname). Media storage auto-switches to Cloudflare R2 (S3-compatible) when `AWS_STORAGE_BUCKET_NAME`/`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` are all set, otherwise falls back to local disk. Optional `GRID_ARCHIVE_BUCKET_NAME` puts the Grid Management archive in a separate bucket (same credentials must reach it). Deployed on Railway (see `Procfile`). `.env.example` lists every variable.
